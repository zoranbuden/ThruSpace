One space. A square, a circle,
and the axes they share.

Every layout engine in common use gives you a rectangle. If you want something arranged around a point instead of inside a box, you go back to writing sine and cosine by hand. ThruSpace makes both frames available at once, in two dimensions or three, and you never name which one you are in.

What you write

ThruSpace.layout('#space', [
  ...ThruSpace.ring('.node', { radius: 78 }),
  { el: '#center', x: 0,  y: 0  },
  { el: '#corner', x: 70, y: 78 }
]);

Eight items on the circle and two in the square, in one call. No mode is declared. angle and radius mean the circle; x and y mean the square.

What it replaces

const n = 8, R = Math.min(w, h) / 2 * 0.78;
for (let i = 0; i < n; i++) {
  const a = (i * 2 * Math.PI) / n;
  el[i].style.left = (w/2 + R * Math.cos(a)
    - el[i].offsetWidth / 2) + 'px';
  el[i].style.top  = (h/2 - R * Math.sin(a)
    - el[i].offsetHeight / 2) + 'px';
}
// re-run on every resize
// redo the maths when n changes

How the space is defined

There is no coordinate mode to select. The frame is inferred from the properties you set, so a single list can mix both, and the two frames stay registered to the same origin.

Square frame

x and y run from −100 to 100, as a share of half the container. The origin is the centre, and y increases upward, the way it does in geometry rather than in screen coordinates.

Circle frame

angle is in degrees from the positive x-axis, radius is 0–100 as a share of the inscribed circle. ring() spreads a set of elements evenly, over a full turn or any arc.

Because every unit is relative to the space rather than fixed in pixels, a layout stays correct when the container changes size without any responsive code of your own.

Where this sits

Constraint solvers already spare you from computing final pixel positions, and they do it well. What none of the mainstream engines offer is a non-rectangular frame.

Ranges instead of fixed values

A constraint solver needs every position to be satisfiable exactly. A range says something looser and more human: put this somewhere between here and there, and sort it out if it collides. Both panels hold the same items at the same angles. The only difference is that the right-hand one gives the radius room to move.

Fixed  

{ angle: a, radius: 45 }

Range  

{ angle: a, radius: [45, 95] }

Add items until the fixed layout breaks. At six or seven it holds up perfectly well — a range is not magic, it is room to manoeuvre for the moment the fixed choice stops fitting. Neither code sample changes.

The third axis

Everything above runs in the plane. Give an element a z and the square it lives in becomes a cube; give it a phi and the circle becomes a sphere. The properties you were already using keep their meaning, so a layout written for the plane returns the same positions it always did. These are ordinary HTML elements, placed by the same engine.

Three dimensions

ThruSpace.layout('#world', [
  ...ThruSpace.ball('.slot', { radius: 78 }),
  { el:'#c1', x:-92, y: 92, z: 92 },
  { el:'#c2', x: 92, y:-92, z:-92 }
]);

Two, for comparison

ThruSpace.layout('#space', [
  ...ThruSpace.ring('.node', { radius: 78 }),
  { el:'#center', x: 0,  y: 0  },
  { el:'#corner', x: 70, y: 78 }
]);

ring becomes ball, and a third number joins the pairs. Nothing else is different, and no coordinate mode is named in either one.

Drag the cube directly, or use the sliders. Items stay square to the viewer while the space around them turns; the corner labels are fixed to the cube, so they turn with it.

An element is also a space

Nothing above treats a container as special. Give any element a space of its own and the same square, circle and axes appear inside it, in its own units, with its own conflict resolution. What follows is one call, three levels deep.

One call

ThruSpace.layout('#nest', [
  { el:'#tile', x:0, y:0, space: [
      { el:'#t1', x:-55, y:0 },
      { el:'#t2', x:  0, y:0 },
      { el:'#t3', x: 55, y:0 }
  ]},
  ...hubs.map(h => ({
      el: h.el, angle: h.angle, radius: 78,
      space: ThruSpace.ring(h.leaves, { radius: 72 })
  }))
]);

Why it matters

The hubs sit on a circle in the outer square. Each hub is a circle in its own right, and the leaves inside it know nothing about the outer space — their coordinates are their own.

This is the part that replaces nesting as most frameworks do it. There is no parent container to declare, no wrapper to insert, and no coordinate to recompute when the outer arrangement changes. The rectangle at the centre is the same mechanism with a square frame instead of a round one.

The whole API

Three functions and five property names. There is nothing else to learn, and nothing to configure before the first call.

Calls

ThruSpace.layout(container, items)
  // items: [{ el, x, y, z, angle, phi, radius, space }]
  // returns { placed, notes, depth }

ThruSpace.ring(selector, { radius, start, end })
  // even spread over a circle or any arc

ThruSpace.ball(selector, { radius })
  // even spread over a sphere

notes tells you which elements the solver had to move and where it put them, which is what the log in the range demo is printing.

Properties

x y−100 to 100, share of half the container
zsame, along the depth axis; its presence makes the frame a cube
angledegrees from the positive x-axis
phidegrees from the axis facing you; 90 is the screen plane
radius0 to 100, share of the inscribed circle or sphere
any of themmay be [min, max] instead of a number
spacea list of items placed inside this element, in its own units

Because no unit is a pixel, a layout holds its proportions at any container size. Call layout again after a resize and the solver settles the ranges afresh.
